Simple JWT Cookie Authentication Demo based on your recent `jwt-cookies` project.

Essential concepts:

- React + TypeScript + Vite frontend.
- Express.js + TypeScript backend.
- Neon PostgreSQL database.
- JWT access token stored in an HTTP-only cookie.
- JWT refresh token stored in a separate HTTP-only cookie.
- Automatic access-token refresh with refresh-token rotation.
- Login, registration, protected dashboard, and logout.
- A backend `.env` file for configuration.


 1. Simple architecture

React + TypeScript + Vite

Login · Register · Dashboard · Axios

[http://localhost:5173]
HTTP requests with credentials enabled

Express.js + TypeScript

Auth routes · JWT · Cookie handling

[http://localhost:5000]

Neon PostgreSQL

Users and hashed refresh-token sessions

The browser manages the HTTP-only cookies. React does not read the JWT values, and the frontend never stores them in `localStorage`.

 4. Important: fix your `.env` before running

Use the following simple configuration in `backend/.env`:

```
PORT=5000
DATABASE_URL=YOUR_NEW_NEON_DATABASE_URL

JWT_ACCESS_SECRET=YOUR_NEW_ACCESS_SECRET
JWT_REFRESH_SECRET=YOUR_DIFFERENT_REFRESH_SECRET

JWT_ACCESS_EXPIRES_IN=10s
JWT_REFRESH_EXPIRES_IN=15m

CORS_ORIGIN=http://localhost:5173
NODE_ENV=development
```

For the teaching demo, the access token expires in 10 seconds, and the refresh token expires in 15 minutes. 
The corresponding cookie lifetimes are configured to match those defaults.

 5. How to run the project

1. Extract AND .
2. Open `backend/schema.sql` and run it in your Neon SQL Editor.
3. Copy `backend/.env.example` to `backend/.env` and enter your new credentials.
4. Start the backend:
   ```
   cd backend
   npm install
   npm run dev
   ```
5. Open a second terminal and start the frontend:
   ```
   cd frontend
   npm install
   npm run dev
   ```
6. Open `http://localhost:5173` in Chrome.

 6. The most important teaching demonstration

Step 1 — Login

The backend validates the password and sets two HTTP-only cookies.

Step 2 — Wait 10 seconds

The access token expires, but the refresh token remains valid.

Step 3 — Call the protected API

The request receives a 401 response. Axios calls `/api/auth/refresh` automatically.

Step 4 — Refresh-token rotation

The backend revokes the previous refresh session, creates a replacement refresh token, issues a new access token, and sets new cookies. Axios retries the original request.

Step 5 — Logout

The backend revokes the current refresh session and clears both cookies.

One important teaching point: refreshing an access token does not mean the original refresh token remains reusable. Rotation replaces the old refresh session with a new one.

Test A — Access-token refresh

Log in, wait more than 10 seconds, then click Call protected API. You should see a loading alert followed by a success toast. The protected request should succeed.



Test B — Refresh-token expiry

Log in and wait more than 15 minutes without refreshing the session. Click Call protected API. You should see the session-expired SweetAlert and, after clicking Go to Login, return to the login screen.



Important: With your current 10-second access-token and 15-minute refresh-token settings, Test B requires waiting over 15 minutes. For classroom demonstrations, temporarily set both token lifetimes to a few seconds in .env, restart the backend, and wait until both tokens expire.
